ORDERFLOW: VERIFIED IMPLEMENTATION AND HOSTED ROLLOUT

Implemented and exercised

- Durable source identities, canonical replay detection and strict envelopes.
- Tenant-scoped current records, immutable revisions and effective intervals.
- Atomic worker effects, terminal receipts/checkpoints and bounded retries.
- Source-authority and same-version conflict protection, including quarantine.
- Server-enforced memberships, roles, keyset pages and protected recovery.
- Real HTTP catalog/event connectors with durable cursor replay.
- A finite mapped Airflow DAG, actual dbt checks and last-good publication.
- Independent inventory comparison with immutable input/report provenance.
- Real process-death recovery and dump/restore/replay verification.
- A responsive React workbench, recorded workflow and public case study.

The release manifest and raw reports define the exact executed scopes. A
passing local release gate does not mean a hosted production rollout exists.

Hosting steps that remain

1. Owner completes Neon marketplace account terms. Vercel is connected, but
   neither backend has a managed database or hosted production workload yet.
2. Provision separate development/production databases and least-privilege
   runtime/transform roles; apply reviewed migrations via an admin connection.
3. Configure a real identity provider, issuer/audience/public key and explicit
   server-side memberships. Keep fixture sessions disabled in production.
4. Establish the worker and finite scheduler on a supported Vercel execution
   model with a verified resource budget. Request functions do not supply an
   always-running consumer. Existing polling processes cannot be assumed to
   survive a serverless request.
5. Configure cross-host object access/retention and scheduled remote backups.
   Rehearse a real remote restore and run the hosted browser-to-database-to-
   worker-to-publication acceptance flow before claiming production behavior.
6. Resolve the GitHub account restriction that currently prevents jobs from
   starting. The installed acceptance workflow is not a successful CI run.

Further improvements, prioritized after hosted acceptance

- Connect one real merchant sandbox and define its authority/version policy,
  pagination, currency/time semantics, rate limits and credential rotation.
- Run a controlled arrival-rate sweep on a reserved host. Measure queue age,
  admission limits, database connections, lock waits, CPU/I/O saturation and
  recovery after a deliberate downstream outage. Keep this distinct from the
  completed closed-loop synthetic core benchmarks.
- Define deployment-specific SLOs and alerts from observed real traffic, with
  explicit failure/queue-age budgets and an operator recovery runbook.
- Add a reviewed terminal-correction workflow that requests a new authoritative
  source version; retain terminal immutability and a complete audit trail.
- Recheck vendor OS advisories and rebuild when fixes appear. The captured
  Python images retain 217 package/advisory pairs each, including 50 high,
  with no fixed versions supplied by the captured distribution database.
- Complete manual screen-reader, keyboard and zoom review with operators;
  automated zero-violation scans alone do not establish WCAG conformance.

These are explicit follow-up work items, not implemented feature claims or
evidence of customer adoption. Source visibility remains an owner decision.
